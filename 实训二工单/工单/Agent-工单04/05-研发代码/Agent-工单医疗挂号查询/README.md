# 健康助理 Agent - 挂号管理模块

本项目实现一个可运行的医疗挂号 Agent。Agent 负责自然语言理解、意图识别、槽位抽取和工具编排；所有数据库查询与写操作统一通过注册工具执行，工具内部使用 SQLAlchemy ORM 和事务处理。

## 项目结构

- `app/agent`：Agent 编排、LLM 封装、规则 fallback
- `app/common`：权限、状态、日志、统一异常与响应
- `app/registration`：ORM 模型、挂号/号源/医生服务、API 路由
- `app/seed_data.py`：测试数据初始化
- `tests/`：核心场景与 30+ 变体测试
- `docs/`：需求、流程、ER、测试报告、实现记录

为什么本项目当前选择 SQLite 而不是 MySQL
本项目当前阶段定位为“健康助理 Agent”的原型系统，其中医院挂号管理只是整体健康助手中的一个业务模块。为了优先保证项目能够快速搭建、便于本地运行、方便演示与测试，数据库选型采用了轻量级的 SQLite，而不是需要独立部署服务的 MySQL。
SQLite 的优势在于不需要额外安装数据库服务，也不需要配置主机、端口、用户名和密码，项目启动后即可直接通过本地数据库文件完成数据读写，特别适合课程作业、功能原型、小型单机应用以及普通办公电脑环境。对于当前这个以“先跑通 Agent 业务流程、验证 Tool Calling + SQLAlchemy ORM 设计”为目标的项目来说，SQLite 能够明显降低部署复杂度，提高开发和调试效率。
相比之下，MySQL 更适合正式生产环境或多用户并发访问场景。它在并发能力、权限管理、服务化部署和可扩展性方面更强，但部署和维护成本也更高。由于本项目当前重点是实现自然语言挂号、号源查询、取消挂号、医生排班查询等核心能力，并不强调大规模并发与生产级运维，因此使用 SQLite 更符合项目当前阶段的需求。
另外，本项目的数据访问层采用了 SQLAlchemy ORM，并通过注册工具统一封装数据库操作，因此后续如果需要升级到 MySQL，只需要调整数据库连接配置和少量适配代码即可，不需要推翻整体系统架构。这种设计既满足了当前阶段的轻量化要求，也为后续扩展到更正式的数据库方案预留了空间。
一句话总结就是：
当前选择 SQLite，是为了降低部署复杂度、提升本地演示效率、优先完成健康 Agent 原型系统的核心业务验证；后续若进入正式系统阶段，可平滑迁移到 MySQL
