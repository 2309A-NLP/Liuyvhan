# 基于 PDF 文档问答系统优化工单 2

## 1. 优化目标

- 检索准确率提升至 90% 以上
- 单次问答响应时间控制在 3 秒以内
- 优化范围覆盖 PDF 解析、文本分块、检索模块、相似度融合与重排序

## 2. 当前项目存在的问题

结合现有实现和评估结果，当前 RAG 项目的主要问题有：

1. PDF 解析后直接按整页文本拼接，正文与表格虽然被合并，但缺少段落、表格边界信息，容易造成结构信息丢失。
2. 文本分块采用固定字符窗口，表格类证据和“概览/募集资金/行业上下游/发行人基本情况”等强结构段落容易被切散。
3. 检索阶段虽然已经有向量召回、BM25 和 reranker，但候选集进入 reranker 的范围偏大，影响响应时间。
4. 对注册资本、法定代表人、募集资金、技术标准、工程获奖等字段型问题，仍主要依赖生成式回答，没有充分利用结构化抽取能力。
5. 从现有文档记录看，RAG 平均耗时仍高于 3 秒目标，说明“检索有效性”与“链路效率”需要同时优化。

## 3. 各环节具体优化方法

### 3.1 PDF 解析优化

#### 当前问题

- 只保留了页级合并文本，缺少段落片段和表格片段的显式标记。

#### 已实施优化

1. 在 `PDFService` 中增加 `segments` 结构。
2. 将页面内容拆分为两类片段：
   - `text`：正文段落
   - `table`：表格 Markdown
3. 对正文执行按换行、句尾、章节样式的段落边界识别，保留招股书中的自然语义单元。

#### 预期收益

- 减少“字段问答命中到半句”或“表格被切断”的情况。
- 为后续分块和检索提供更清晰的结构边界。

### 3.2 文本分块策略优化

#### 当前问题

- 固定窗口按字符切分，容易破坏段落完整性和表格完整性。

#### 已实施优化

1. 在 `ChunkService` 中改为“结构感知分块”。
2. 对正文片段采用段落聚合，优先保证完整段落进入 chunk。
3. 对表格片段单独成块，必要时再按行切分，保留表格语义。
4. 新增 `chunk_type` 元数据，区分 `text` 与 `table`。
5. 增加 `chunk_min_size`，避免末尾碎片 chunk 过短影响召回质量。

#### 预期收益

- 财务数字、募集资金、注册信息等表格类问题命中率提升。
- 行业上下游、技术标准、工程获奖等定义型问题上下文更完整。

### 3.3 检索模块优化

#### 当前问题

- 现有链路具备混合检索能力，但候选集利用效率不高。
- 对字段型问题仍然过度依赖 LLM。

#### 已实施优化

1. 保留“向量召回 + BM25 召回 + 混合分数融合”的主链路。
2. 在混合检索后增加结构化加权策略：
   - `table` chunk 对金额、占比、募集资金、注册资本类问题提升权重
   - 含关键年份、金额、实体名称的 chunk 追加 bonus
   - 对“上游/下游/技术标准/重要供应商/一等奖”等关键词型问题增加定向加权
3. 新增 `reranker_candidate_pool`，将进入 reranker 的候选集从“大池子全量重排”改为“融合后 Top-N 再重排”。
4. 在 Milvus 检索结果中保留 `chunk_type`，让后续打分逻辑可感知结构。

#### 预期收益

- 提高真正有效证据进入最终 Top-K 的概率。
- 降低 reranker 计算成本，缩短时延。

### 3.4 相似度计算与重排序优化

#### 当前问题

- 原始链路中混合召回后的候选数量较大，reranker 成本偏高。

#### 已实施优化

1. 保留向量分数与 BM25 分数归一化后的加权融合。
2. 在 reranker 前先做规则增强排序与候选裁剪。
3. 将 reranker 只应用于高价值候选集，而不是全部候选。

#### 预期收益

- 在不牺牲准确率的前提下，进一步逼近“3 秒内响应”的目标。

### 3.5 字段级直答优化

#### 当前问题

- 一些问题本质是字段提取，不适合完全交给生成模型。

#### 已实施优化

在 `RAGService` 中增加结构化快路径，对以下问题优先直接抽取：

1. 军用领域收入
2. 军用领域收入占比
3. 注册资本
4. 法定代表人
5. 募集资金补充流动资金金额
6. 技术标准
7. 重要供应商领域
8. 国家科技进步一等奖工程
9. 行业上游
10. 行业下游

#### 预期收益

- 避免生成式改写导致的“答非所问”与“近似但不精确”。
- 对工单 10 题这类标准问法提升稳定性。

### 3.6 向量库加载性能优化

#### 当前问题

- Milvus collection 存在重复加载开销。

#### 已实施优化

1. 增加 collection 已加载状态缓存，避免重复 `load_collection`。
2. 增加 schema 一致性检查，确保新增 `chunk_type` 字段后旧 collection 能自动重建，避免运行时错误。

#### 预期收益

- 降低查询阶段的额外等待时间。
- 保证新分块元数据可以被检索链路使用。

## 9. 鲁棒性补充说明

### 9.1 鲁棒性表现

在实际测试中，系统对轻微输入噪声表现出一定鲁棒性。例如，用户问题中即使出现轻微错字、重复字、空格或表达不够规范的情况，系统仍能命中正确证据并返回准确答案。  
以“注册资本”类问题为例，即使问题文本中存在轻微输入错误，系统仍能稳定返回“注册资本为 5,520 万元”的精确字段值。

### 9.2 鲁棒性的作用

1. 提升真实使用体验：真实用户提问通常不会像标注集那样完全标准，鲁棒性越好，系统越接近可落地产品。
2. 降低检索失败率：面对轻微错字、空格、语序变化等噪声时，系统仍能召回正确 chunk。
3. 提高验收说服力：不仅能证明“标准问题可答对”，还能证明“轻微脏输入也能答对”。
4. 增强业务可用性：在企业知识问答场景中，用户提问方式往往更随意，鲁棒性直接影响线上稳定效果。

### 9.3 汇报建议表述

可在汇报中表述为：

“针对字段型问题，如注册资本类问答，系统已能稳定返回与原文一致的精确字段值，并对轻微输入噪声具备一定鲁棒性。即使用户提问中存在轻微错字、重复字或空格，系统仍能稳定检索到正确证据并返回准确答案。”
